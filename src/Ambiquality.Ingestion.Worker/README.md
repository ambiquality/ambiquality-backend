# Ambiquality.Ingestion.Worker

Background worker that **materializes** the ingestion queue: it drains the durable Redis
stream that `Ambiquality.Ingestion.Api` writes and bulk-inserts the measurements into the
`ieq.measurements` TimescaleDB hypertable. The API accepts and enqueues; this worker is the
only writer of the hypertable (F10).

This is the read side of the **queue + worker** write path. Splitting accept-from-sensor
(the API) from persist-to-DB (this worker) lets write spikes be absorbed by the queue instead
of coupling to request throughput, serving the ≥ 100 measurements/s ingestion NFR.

## How it works

1. **Consumer group** — on startup the worker ensures the stream's consumer group exists,
   then joins it under a unique consumer name (`{machine}-{guid}`).
2. **Drain** — `MeasurementDrainService` (a `BackgroundService`) reads new entries for the
   group with `XREADGROUP`, in batches. StackExchange.Redis has no blocking `XREADGROUP`, so
   the loop polls on `MeasurementQueueOptions.BlockMilliseconds` when the stream is idle and
   loops immediately while entries are flowing.
3. **Write** — each batch is bulk-inserted by `MeasurementBatchWriter` in a single round trip
   with `ON CONFLICT (id, received_at) DO NOTHING`. The measurement id is generated by the API
   at enqueue, so the at-least-once queue plus the idempotent insert give an exactly-once
   effect — a redelivered entry is harmlessly skipped.
4. **Acknowledge** — only entries whose rows were durably written are `XACK`-ed. A crash
   between write and ack merely redelivers entries the idempotent writer skips, so nothing is
   lost and nothing is double-counted.
5. **Recover** — on startup and periodically the worker reclaims entries left pending by a
   crashed consumer with `XAUTOCLAIM`, so no measurement is stranded if a consumer dies
   mid-batch.

`received_at` is stamped by the **API** at acceptance (before enqueue) and survives the queue
byte-for-byte, so however long the queue takes to drain, the recorded ingestion time — the
hypertable's partition key — never shifts.

## Data access

No EF Core on the write path: the bulk insert is raw Npgsql, the same pattern as
`Export.Worker`. The worker connects to `ieq` as the `ingestion_api` role (read/write). The
`measurements` hypertable, its composite key `(id, received_at)` and `parameter_ranges` are
owned by `Ambiquality.Ingestion.Api`'s `IeqDbContext` migrations pipeline; this worker only
writes rows, it does not own or run migrations.

The shared wire contract is `Core/Messaging/MeasurementMessage` (+
`MeasurementMessageSerializer`); stream key, group name and batch sizing live in
`MeasurementQueueOptions`.

## Running

```bash
dotnet run --project src/Ambiquality.Ingestion.Worker   # needs the ieq db + Redis
```

In the stack it runs as the `ingestion-worker` compose service alongside Redis and the
`ingestion-migrate` container that provisions the hypertable.
